# Implementation Plan: MOF HR Chatbot (MOF HR แชท)

**Branch**: `main` | **Date**: 2026-05-15 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-mof-hr-chatbot/spec.md`

---

## Summary

Build "MOF HR แชท" — a local-only HR policy chatbot for the Ministry of Finance
(กระทรวงการคลัง) Thailand. HR staff type questions in Thai; the chatbot searches
`data/thai_leave_policy.pdf` via Azure AI Foundry's File Search tool and responds in
semi-formal Thai. The app is a Vite-served single-page web application using vanilla
HTML/CSS/JS with a lightweight Node.js server middleware (via Vite's `configureServer`
plugin) to proxy requests to Azure AI Foundry. Conversation history is limited to the
last 5 turns, managed as a client-side sliding window in browser memory with no
external database.

## Technical Context

**Language/Version**: Node.js 18+, JavaScript ES2022 (vanilla, no framework)

**Primary Dependencies**:
- `vite` ^5 (devDependency — build tool + dev server with custom middleware)
- `@azure/ai-agents` ^1.1.0 (existing — Foundry agent + file search)
- `openai` ^4.73.0 (existing — `AzureOpenAI` client used with API-key auth)
- `dotenv` ^16.4.5 (existing — env var loading)
- `vitest` ^2 (devDependency — test runner, Vite-native)

*No additional runtime libraries. No Express. No React. No Vue.*

**Storage**: In-memory only.
- Client: `history` array in browser JS (sliding window, max 10 messages)
- Server: `FoundryAgentContext` singleton in Node.js process (agentId, vectorStoreId, fileId)
- No database, no localStorage, no sessionStorage, no file writes

**Testing**: Vitest (unit + integration)

**Target Platform**: Local browser via Vite dev server (http://localhost:5173). macOS/Windows developer machine. No cloud deployment for Phase 1.

**Project Type**: Web application (single-service, Vite-served, locally run)

**Performance Goals**:
- Agent API response ≤ 30 s (SC-001, FR performance requirement)
- Application ready-to-use ≤ 3 s after `npm run dev` (excluding Azure init, SC-005)
- Memory: single Node.js process < 256 MB resident (Constitution Principle IV)

**Constraints**:
- Maximum 5 conversation turns retained in context (FR-004)
- Maximum message length: 2000 characters
- No external DB or vector DB (FR-002; use Foundry File Search only)
- Credentials via `.env` only — never hardcoded (FR-011)

**Scale/Scope**: 1–2 concurrent users, PoC phase, local-only

## Key Design Decisions

### 1. Vite `configureServer` plugin for API routes

`vite.config.js` defines a plugin that registers Node.js connect-style middleware for
all `/api/*` routes. The middleware is imported from `server/foundry.js`, which has
full access to Node.js APIs, the file system, and the Azure SDKs. No Express is needed.

```js
// vite.config.js (sketch)
import { createFoundryMiddleware } from './server/foundry.js'

export default defineConfig({
  plugins: [{
    name: 'hr-chat-api',
    configureServer(server) {
      server.middlewares.use('/api', createFoundryMiddleware())
    }
  }]
})
```

### 2. Foundry integration follows `src/02_file_search.js` exactly

`server/foundry.js` replicates the upload → vector store → agent → thread → run →
list messages pattern from the existing example. The agent is created once (lazy, on
first POST `/api/chat`) and cached for the lifetime of the Vite process.

```js
// server/foundry.js (pattern sketch)
const { AzureOpenAI } = require('openai')

let ctx = null  // FoundryAgentContext singleton

async function ensureAgent() {
  if (ctx?.initialized) return ctx
  const client = new AzureOpenAI({
    endpoint: process.env.FOUNDRY_ENDPOINT,
    apiKey: process.env.FOUNDRY_API_KEY,
    apiVersion: '2025-01-01-preview',
  })
  // upload PDF, create vectorStore, create assistant (exact 02_file_search.js pattern)
  ctx = { client, assistantId, vectorStoreId, fileId, initialized: true }
  return ctx
}

async function handleChat(req, res) {
  const { message, history } = JSON.parse(body)
  // validate inputs
  const { client, agentId } = await ensureAgent()
  const thread = await client.threads.create()
  for (const m of history.slice(-MAX_HISTORY_MESSAGES)) {
    await client.messages.create(thread.id, m.role, m.content)
  }
  await client.messages.create(thread.id, 'user', message)
  const run = await client.runs.createAndPoll(thread.id, agentId, {
    pollingOptions: { intervalInMs: POLL_INTERVAL_MS }
  })
  // extract reply and return { reply }
}
```

### 3. Client-side 5-turn sliding window

`app/main.js` maintains a `history` array. `MAX_TURNS = 5` is a named constant.
Before each request, the last `MAX_TURNS * 2` messages are sent as `history`.
After each reply, the array is trimmed back to `MAX_TURNS * 2` items.

### 4. System prompt (Thai, semi-formal)

The Foundry agent's `instructions` field is set to a Thai-language system prompt
stored as the named constant `SYSTEM_PROMPT` in `server/foundry.js`. This enforces
FR-003 and the meeting's language requirement at the agent level, not just the UI.
